# 首次整理与旧聊天补录

先查正式状态及当前原文实际覆盖。聊天恢复事件不是“空白新聊天”的证据，也不能把没有档案等同没有历史。

continuous适用于已有正式档案，覆盖当前压缩阶段起点至本次整理；没有新压缩时更新同一阶段，不从上次蒸馏截止开始。first_visible适用于首次整理且本次范围原文完整可见，准确记录起点。bootstrap适用于旧聊天已经压缩但未整理，或阶段链中有缺口。stage_key和旧档案衔接见storage.md。

补录仍产出原有阶段与接手两类单元。阶段正文忠实记录直接核实范围，更早概括标为历史参考及来源类别。接手累计整合仍有价值的结论、偏好、成果、经验及材料。压缩前最后一稿未覆盖的尾段如实记缺口，不因已发生压缩强制补写。两位检查官对照实际可用材料，不声称核实过缺失原文。

coverage JSON的四个原字段继续填写。补录还需以下字段，history_sources和known_gaps用非空列表，scope_confirmation记录当前用户已同意的范围。

```json
{
  "mode": "bootstrap",
  "start": "直接可核实原文起点",
  "end": "本次整理请求的准确定位",
  "previous_compaction": "可核实的最近压缩定位，未知时写明",
  "original_visibility": "哪些内容为直接原文，哪些来自继承摘要",
  "history_sources": [{"kind": "inherited_summary", "locator": "当前上下文的继承摘要", "scope": "实际覆盖范围"}],
  "known_gaps": ["更早压缩前细节未逐项核实"],
  "scope_confirmation": {"message_ref": "真实用户消息定位", "user_text": "用户原话"}
}
```

直接读取旧接手供新聊天理解时，只读即可，不自动begin、不冒用旧UUID。真正在新聊天蒸馏时，使用其当前UUID，将旧接手登记为外来历史来源。原项目/原聊天档案不因新聊天接手而被覆盖。

用户要求补原记录时再按指定范围读取，批量翻所有日志不是默认流程。原记录存在、已读到、已核对是不同状态，材料表如实记录。
